Commands & Skills

Your automation vocabulary — recipes and knowledge cartridges

Commands: keyboard shortcuts for entire workflows

Imagine you're a chef. Instead of explaining the entire risotto recipe every time someone asks for it, you just say "make the risotto." The recipe is already written down — you're just invoking it by name.

That's a command. It's a .md file full of instructions Claude follows when you type /its-name. Write it once, use it forever.

📁
Where commands live

Commands go in .claude/commands/ inside your project. Each file becomes a slash command — the filename is the command name.

Anatomy of a command

Here's a real command from the repo — the weather orchestrator. Let's read it line by line.

weather-orchestrator.md 
---
description: Fetch weather for Dubai
model: haiku
---

## Workflow

### Step 1: Ask User Preference
Use AskUserQuestion to ask
whether they want Celsius
or Fahrenheit.

### Step 2: Fetch Weather Data
Use the Task tool to invoke
the weather-agent...

### Step 3: Create SVG Card
Use the Skill tool to invoke
weather-svg-creator skill.
PLAIN ENGLISH

description: A one-line summary of what this command does. Claude reads this to know when to suggest it.

model: haiku — Use the faster, cheaper model for this command. You can override the model per command.

Step 1 — First, ask the user a question before doing anything. This makes the workflow interactive.

Step 2 — Spawn a specialized subagent (weather-agent) to go fetch the actual data. The command orchestrates; the agent does the work.

Step 3 — Load a skill (weather-svg-creator) to generate the visual output. Each step hands off to the right specialist.

Skills: knowledge cartridges you snap in

A skill is like a removable memory chip. It contains specialized knowledge — instructions for a specific task — that gets loaded into Claude's context when needed, and removed when it's done.

The key idea: instead of one giant brain that knows everything, you have a lean base plus skill files you snap in on demand.

📦

Agent Skills

Preloaded into a subagent via its skills: field. The agent always has this knowledge available.

🛠️

Invocable Skills

Triggered via Skill(skill: "name"). Claude loads the skill, follows its instructions, then continues.

03

Subagents

Autonomous workers with their own tools, memory, and limits

Hiring a contractor, not asking a colleague

When you ask a colleague for help, they know everything about your shared project — your history, your ongoing work, your conventions. But sometimes you want to hire a contractor instead.

A contractor shows up, does a specific job with their own tools, and leaves. They don't need to know everything about your company — just the task at hand. That's a subagent.

🤝

Main Session

Knows your whole project. Has your full conversation history. Works interactively with you.

🏗️

Subagent

Isolated context. Custom tools. Its own permission level. Runs a task and returns a result. Can run in parallel with others.

Configuring your contractor

You configure a subagent through frontmatter — a short block of settings at the top of the agent file. Here's the real weather-agent:

weather-agent.md (frontmatter) 
---
name: weather-agent
description: Use PROACTIVELY when
  you need Dubai weather data.
model: sonnet
maxTurns: 5
permissionMode: acceptEdits
memory: project
color: green
skills:
  - weather-fetcher
---
PLAIN ENGLISH

name: The ID Claude uses when another agent or command wants to spawn this worker.

description: PROACTIVELY — That keyword tells Claude to suggest or auto-use this agent when the situation calls for it.

model: sonnet — Use the smarter (but slower) model. You can tune this per-agent for cost vs. quality.

maxTurns: 5 — This agent is allowed to take at most 5 action steps. A safety guardrail so it can't spiral forever.

permissionMode: acceptEdits — The agent can edit files without asking you. Useful for automated workers.

memory: project — This agent can read and write to the project-level memory store between sessions.

skills: weather-fetcher — Load this skill into the agent's context from the start. The agent always knows how to call the weather API.

The fields that matter most

A subagent has 16 possible configuration fields. Here are the 6 you'll use in almost every agent:

🎯

description

Tells Claude when to invoke this agent. Add "PROACTIVELY" to make Claude auto-suggest it.

🔧

tools (allowedTools)

Exactly which tools this agent can use. Bash(*), Read, WebFetch(*), etc. Limits scope.

🛡️

permissionMode

acceptEdits — auto-approve edits. plan — show plan, don't act. bypassPermissions — full trust mode.

🔢

maxTurns

Maximum action steps before the agent stops. Your safety net against runaway automation.

🧠

memory

user, project, or local — determines what persistent memory this agent can access and write.

⚡

isolation: worktree

Runs the agent in its own git worktree — a separate branch copy. Safe for risky experiments.

Memory & Settings

Teaching Claude your world — and setting its guardrails

The employee handbook Claude reads every morning

Every new employee reads the company handbook on day one. It tells them: what we do, how we work, what's allowed, what's not. They don't need to be re-trained every day — the handbook sticks.

CLAUDE.md is Claude's handbook for your project. It's a Markdown file at the root of your project. Claude reads it at the start of every session. Everything you write there becomes persistent context — no re-explaining needed.

💡
What goes in CLAUDE.md?

Project architecture, coding conventions, which commands exist, which agents do what, debugging tips, commit rules, or anything you'd tell a new developer on your team. Keep it under 200 lines — Claude reads it in full every time.

Three layers of memory

CLAUDE.md files form a hierarchy. Claude loads them from the broadest (global) to the most specific (local subfolder) — like concentric circles of context.

🌍
Global Memory

~/.claude/CLAUDE.md — Your personal rules that apply to every project on your machine. Think: preferred code style, your name, how you like things formatted.

📁
Project Memory

./CLAUDE.md — Rules for this specific project. Architecture decisions, team conventions, key components. Shared with your whole team via git.

🔒
Local Override

./CLAUDE.local.md — Personal overrides for this project. Your own debugging notes, secret preferences. Not committed to git.

🗂️
Monorepo superpower

In a monorepo, each subfolder can have its own CLAUDE.md. When you work in packages/api/, Claude automatically loads that folder's CLAUDE.md on top of the root one.

Permission rules: your safety fences

You control exactly what Claude is allowed to do. The permission system has three modes: allow (no prompt), ask (confirm first), and deny (blocked entirely).

Here's the real .claude/settings.json from this repo:

.claude/settings.json (permissions) 
{
  "permissions": {
    "allow": [
      "Edit(*)",
      "Write(*)",
      "Bash(*)",
      "WebFetch(domain:*)"
    ],
    "ask": [
      "Bash(rm *)",
      "Bash(npm *)",
      "Bash(docker *)"
    ],
    "deny": []
  }
}
PLAIN ENGLISH

allow: Edit(*), Write(*), Bash(*) — Claude can freely edit files and run terminal commands without asking each time. The * is a wildcard meaning "any argument."

allow: WebFetch(domain:*) — Claude can fetch any URL without confirmation. Useful for API calls and research.

ask: Bash(rm *) — Before running any delete command, stop and ask for confirmation. Even in "auto" mode.

ask: Bash(npm *), Bash(docker *) — Package installs and container operations require human approval. Prevents surprise dependencies.

deny: [] — Nothing is fully blocked in this config. In a stricter environment you might deny Bash(chmod *) or Bash(kill *).

Hooks: the logic that never hallucinates

Everything we've covered so far — commands, agents, skills — is AI-driven. But sometimes you need guaranteed, deterministic behavior. A sound when Claude finishes. A log entry on every file change. A security check before every terminal command.

That's what hooks are for. They run outside the AI loop — no hallucinations, no "maybe I'll do this." Just code that executes.

🔔

Notifications

This repo plays a sound when Claude finishes a task, when a subagent starts, when a permission is requested. Pure Python, 100% reliable.

🛡️

Security Checks

Run a script before every Bash() call to validate commands. Block dangerous patterns before they execute.

📝

Audit Logs

Write every tool use to a log file. Know exactly what Claude did, when, and what arguments it passed.

🔄

Auto-compaction

Trigger a /compact at 80% context usage before Claude forgets your conversation history.

⚡
Hook events in this repo

The repo configures 20+ hook events: PreToolUse, PostToolUse, SessionStart, SessionEnd, SubagentStart, Stop, FileChanged, ConfigChange, and more. Every one triggers the same Python script, which routes to the right handler.

The Full Stack

MCP servers, the orchestration pattern, and power moves

MCP: USB ports for your AI

Out of the box, Claude can read and write files, run terminal commands, and browse URLs. But what if you need it to search your database, control a browser, or call your company's internal API?

That's what MCP servers are for. They're like USB ports: plug one in, and suddenly Claude can do things it couldn't before. Pull it out, and that capability disappears.

.mcp.json (real config) 
{
  "mcpServers": {

    "playwright": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp"]
    },

    "context7": {
      "command": "npx",
      "args": ["-y", "@upstash/context7-mcp"]
    },

    "deepwiki": {
      "command": "npx",
      "args": ["-y", "deepwiki-mcp"]
    }
  }
}
PLAIN ENGLISH

mcpServers — A list of external capabilities to give Claude. Each entry is a named server with instructions for how to start it.

playwright — Gives Claude the ability to control a real web browser. It can click buttons, fill forms, take screenshots, and read page content.

command: npx / args: [...package] — "To start this server, run this npx command." MCP servers are just programs — they can be written in any language.

context7 — Connects Claude to documentation databases. When you ask about a library, Claude can look up the latest docs instead of guessing from training data.

deepwiki — Lets Claude read GitHub repositories as structured knowledge, not just raw file content.

Local vs remote MCP servers

There are two ways to connect an MCP server. Choose based on where the tool lives:

💻

Local (stdio)

The server runs on your machine as a process. Claude talks to it via standard input/output. Playwright, context7, and deepwiki all work this way.

"command": "npx", "args": ["..."]

🌐

Remote (HTTP)

The server lives at a URL — your company's API, a third-party service, or a cloud-hosted tool. Claude calls it over HTTPS.

"type": "http", "url": "https://..."

🔑
Scoping MCP to specific agents

You can give an MCP server to just one subagent via its mcpServers: frontmatter field. The main session doesn't get browser access — only the agent that needs it does. Principle of least privilege.

Power moves you can use now

Once you understand the full system, these patterns unlock serious leverage:

🏃

Agent Teams

Spawn multiple agents in parallel — each working on a separate repo, feature, or task. Finish in 1/N the time.

⏰

Scheduled Tasks

/loop 5m repeats a task every 5 minutes locally. /schedule sets up cloud-hosted cron jobs that run even when your laptop is closed.

🌿

Git Worktrees

Give each agent its own isolated branch copy. Multiple agents can modify different parts of the codebase simultaneously without conflicts.

⚡

Fast Mode

Toggle /fast for the same Claude Opus model but with faster output streaming. Same intelligence, better UX.

🩺

Debugging: /doctor

Run /doctor to diagnose Claude Code configuration issues. When things break, start here before anything else.

🗜️

Manual Compact

At ~50% context usage, run /compact manually. Keeps your conversation history tight and prevents context overflow mid-task.
